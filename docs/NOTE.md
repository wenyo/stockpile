建議的原則是：**一次修一個問題，每個問題走同一套固定流程**。

## 一、動手前先整理清單

1. **處理「待驗證」的項目。** 有些問題是推論，不是實測確認的。例如「使用範例會清空成員與標籤」，可以先自己重現：開啟 app → 在歡迎視窗選「探索範例」→ 點頂端的「退出 Demo」→ 選「使用範例」→ 看設定頁有沒有成員、儀表板天數是否為 0。重現不了就從清單劃掉。
2. **先做產品決策。** 像「到期當天算不算已過期」「低庫存門檻要不要依類別不同」，這些會改變使用者看到的數字，要由你決定，不要讓 Claude 默默選。
3. **建立基準。** 在乾淨的 git 狀態下跑 `npm run typecheck` 與 `npm run build`，記下結果，並用「備份資料」匯出一份你的真實資料。

## 二、建議的處理順序

| 順序 | 內容 | 原因 |
|---|---|---|
| 1 | 影響數字正確性的問題（零庫存、熱量不分類別、到期定義） | 使用者直接看到的結果，且改動小 |
| 2 | 資料保護（匯入驗證、`JSON.parse` 防護、Demo 流程） | 避免資料遺失 |
| 3 | 測試與 CI（typecheck 納入 workflow、核心計算補測試） | 之後重構才有安全網 |
| 4 | 架構重構（儲存層、統計提升到 Provider、拆大檔） | 風險最高，放到有測試之後 |
| 5 | 無障礙與操作細節（modal、hover 按鈕） | 彼此獨立，可以最後處理 |

重構一定要排在補測試之後，否則改完你無法確認行為有沒有變。

## 三、每個問題的處理流程

1. **開新分支或確認在正確分支**，工作區乾淨。
2. **先重現。** 能寫成測試就寫測試，並確認它是失敗的；不能的話，寫下手動重現步驟。
3. **牽涉多個檔案時先用 plan mode**，讓它列出會動哪些檔案，你確認後再執行。
4. **實作最小改動。** 只改這個問題需要的地方。
5. **跑 `typecheck`、`build` 與測試。**
6. **看 diff**，確認沒有改到範圍外的檔案，也沒有為了通過而改測試或弱化斷言。
7. **自己操作 app 驗證**，用重現步驟再跑一次。
8. **更新 `docs/ISSUES.md` 的狀態**，一個問題一個 commit，commit 訊息帶上問題編號。
9. **`/clear` 後再處理下一個**，避免上下文混在一起。

給 Claude 的指令範本：
```text
請處理 docs/ISSUES.md 的 ISSUE-001。
1. 先寫一個會失敗的測試重現問題，確認後再修
2. 只修改與此問題直接相關的檔案
3. 完成後跑 typecheck 與 build，並說明你改了哪些檔案、刻意沒動哪些
4. 把 ISSUE-001 的狀態更新為「已修正」
```

## 四、需要特別注意的事

- **數字會變。** 修到計算邏輯後，使用者看到的天數可能改變，值得在版本說明裡寫一句，並考慮升版號。
- **先別打 tag。** 你的部署是推 `v*` tag 才觸發，每批都驗證完再打。
- **資料格式有變就要遷移。** 舊使用者的 localStorage 還是舊格式，用你備份的舊版 JSON 測試匯入與升級。
- **PWA 要用 build 後的版本實測。** 開發模式與正式版的 service worker 行為不同，離線與更新相關的修改要在 build 後驗證。
- **不要同時平行修。** 好幾個問題都會動到 `useDashboardStats.ts` 和 store，同時進行容易衝突。若要用 worktree 平行，挑互不重疊的問題。
- **範圍外的發現不要順手改。** 請 Claude 把它記到清單，之後另外處理。
- **失敗兩三次就停。** 同一個問題反覆修不好，改成請它先解釋根因、縮小範圍，或你自己介入，不要讓它一直試。
- **測試失敗先判斷是誰錯。** 是程式錯、還是測試本身寫錯，不要讓它直接改測試讓結果變綠。
- **出問題就 `git revert`。** 因為每個問題一個 commit，回退很乾淨。
